# Refine Workflow

Use the `refine_workflow` tool from the active Pi session. Supply frozen requirements/trace, Gold, the complete Active Skill, deterministic rules, and an output root.

The workflow is strict:

1. Description reconstruction reads only requirements and deterministic rules.
2. Current Draft reads Description plus Active Skill. It must never read Gold or evaluation artifacts.
3. A Workflow-private ExPerT runs as a top-level auxiliary-evidence node before the sibling Reviewer stage and compares Current Draft with Gold. Its gaps do not gate what the Reviewer may observe or turn into a Finding.
4. Reviewer uses one persistent Pi session for three semantic rounds. Round 1 reads all five inputs and covers the opening, every major Description section/group, cross-section organization, conclusion, and delivered register before declaring `REVIEW_ROUND_1_READY`; a short local issue list is not sufficient coverage. Round 2 actively challenges the first pool, checks Draft counterevidence, semantic Active Skill duplication, Description conflicts, Gold-only details, and missed document functions, then declares `REVIEW_ROUND_2_READY`. Round 3 alone submits at most five reusable Findings. A candidate referenced by uncertainty cannot remain a Finding. Semantic duplicates never compile, refinements name the precise line-local increment, and Description-required repetition across body, comparison, and conclusion cannot be centralized away. Final submission is one bare JSON object; format corrections continue in the same session and change structure only, not the completed semantic judgment.
5. If Reviewer returns no attributable style-method findings, copy the Active Skill as a no-op audit artifact and reject immediately. Otherwise Policy Optimizer directly reads the frozen Description as well as the complete Active Skill and Review; it does not trust Reviewer paraphrases as the content contract. It skips duplicates and Description conflicts, line-locally merges refinements into the named nearest rule, rewrites conflicts at that same canonical location, and adds a new rule only when no semantic equivalent exists. Description-required functional repetition, slots, and concrete values are non-regression boundaries. Every changed or deleted line must directly implement a Finding. Preserve frontmatter, source comments, file indexes, unrelated sections, and non-conflicting wording verbatim—do not perform opportunistic cleanup or generalization.
6. Current and Candidate Draft generation first inventories Description-required content slots and concrete values and freezes explicitly prescribed sections/groups, their order, enumerated members, and membership. Compression, concision, structural unification, or register cleanup may change presentation and remove repetition or meta narration only; it must not add, remove, merge, or re-root contract structure/members or replace required values with generic equivalents. Before delivery, verify the frozen contract item by item, then perform one pass for a single canonical spelling of each term, proper name, and entity. Candidate Draft still must never read Gold.
7. Candidate ExPerT and an independent Judge compare Current and Candidate outcomes against Gold. The Judge uses one persistent Pi session: it first reads and compares every frozen input, then submits the structured Artifact in a later turn; any format correction continues in that same session. It emits auditable slot checks for the opening, every Description-required section/group/value, conclusion, and cross-document consistency, plus a Candidate-specific regression list. It must detect a deleted opening conclusion set, conditional claims generalized into universal requirements that contradict later paths, and author-facing writing instructions left in the delivered document; shared issues belong in the reason rather than the Candidate-only list. A Gold-only factual difference that Description did not require is background, not a standalone regression. Verdict, scores, Hard Pass semantics, and promotion thresholds remain unchanged. The Judge only localizes visible document differences and cannot infer whether Skill rules or Draft execution caused them because it does not read Review or Candidate Skill.
8. A deterministic decision stage emits `promote` or `reject` from Skill-change, attributed-Finding, and deterministic Expert gates. The Independent Judge always runs and its Artifact or failure evidence is preserved, but its verdict is advisory and never blocks promotion by itself. Harness self-evolution is triggered only when Candidate Expert `f1` is strictly lower than Current Expert `f1`; equality is not a regression.
9. Never overwrite the Active Skill in this demo. A non-Expert rejection does not trigger Harness self-evolution; strict deterministic Expert `f1` regression is the only trigger.

Use `refine_workflow_cards` and the Workflow manifest to inspect pinned role identities, contracts, and stage lineage. `refine_workflow` is the product Refine entry point.

An optional learned Task-family Harness Profile can add one short role-specific instruction to Reviewer, Aspect Extractor, Directional Matcher, Evidence Aligner, or Policy Optimizer. Supply both `taskType` and `harnessProfilePath`. The Demo Profile selects exactly one role and one `agent_card`, `prompt`, or `skill` surface. The Workflow starts from the current base Card and current stage protocol, then supplies the Profile's task conditions, negative controls, activation condition, and instruction to the selected role. A different `taskType`, an unmet task condition, or a matching negative control leaves the instruction inactive. Profiles never replace the three-round Reviewer topology, modify Draft or Judge, or change the deterministic Expert Reducer.

Do not introduce a baseline business input. Use `draft` and `candidateDraft` for the two generated documents.
