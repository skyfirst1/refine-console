# Harness audit operating Skill

The Harness operating instructions live in `.pi/skills/refine-harness-audit/SKILL.md`. `src/harness-audit-skill.ts` loads the actual checkout file (the bundled copy is the fallback for other working directories), records its digest, and renders the instructions delivered to the model. The Skill audits role behavior; it does not alter Expert content/style judgments.

`runRefineTaskBehaviorAudit` uses this same Skill during its existing persistent audit phases and writes `harness-operating-skill.json`. Callers may supply `taskPurposes`, with task identifiers, content/style purposes and source-authority descriptions. Undefined axes remain null; there is no task-name classification table.

`runExpertBoundaryFindingAudit` is the diagnostic projection for existing public Expert traces. It uses the same operating Skill, purpose renderer, Pi runner and caller-selected trace tools. It reports findings without forcing them through Profile compilation. The caller owns the frozen public trace batch, output schema, budgets and existing checkpoint. This projection does not run Refine, extract Aspects or compress traces.

For evaluations, freeze the Skill and task purposes before reading private Gold findings. Confirm the actual model request contains both the Skill and purposes; a file hash alone does not prove delivery. Keep a historical instruction's execution correctness distinct from its suitability for a newly declared purpose. Diagnostic findings need not imply a new actionable overlay.

`runHarnessBoundaryExtraction` is an optional independent Pi session before the diagnostic Harness. Its input is the actual Description, explicit user boundary and migration goal. Its cache binds that input, the extraction instruction and model configuration; an incomplete or failed cache is retained rather than automatically regenerated. A changed semantic input creates a separate cache identity.

The diagnostic entry accepts optional `generatedBoundaries`. These are fallible interpretations, not Expert runtime instructions or higher authority than the user. The Harness receives both the original task purposes and generated table, checks their provenance and conflicts, and retains uncertainty. Missing optional output decoration does not erase a valid boundary table; source/event identity must remain explicit.

The prose evaluation-Skill generator also accepts `evaluationMethod: "local-evidence-v1"` with a versioned workflow. This optional first-layer instruction asks for stage-local evidence and uncertainty rules, separates concept presence from values and authority, and distinguishes comparability from best or unique selection. It does not receive a local trace or expected finding. Its instruction and schema create a separate cache identity; omitting the option preserves the previous generator and cache. The generated Skill remains a fallible criterion for the unchanged downstream Harness, not an Expert runtime update or proof of semantic quality.

`runHarnessFindingRevision` in `src/harness-finding-revision.ts` is an optional second Harness after a frozen diagnostic response. It starts an independent Pi session through the shared audit entry. Supply the complete first response, complete local comparisons and attempts, current task purposes, generated evaluation Skill, and materialized artifact identities. The caller still owns evidence selection, budgets and durable checkpoints. The entry preserves raw prose, including qualifications outside finding arrays; it neither applies changes nor retries formatting.

The second stage revises first-stage claims and may propose Expert Card, Expert operation/evaluation Skill, or behavior-badcase changes. Each Card/Skill candidate names its actual artifact and role. Writing, Harness-operating and coordinator Skills are not editing targets. A first-Harness error remains a revised diagnosis rather than evidence for an Expert patch. Badcases are candidate behavior records bound to real inputs, not private Gold labels or an implemented regression consumer.

The result is a proposal, not a compiled Profile. Existing Profile validation permits one role and one `agent_card`, `prompt` or `skill` surface; multiple candidates require separate consideration, and behavior badcases have no Profile surface. This entry does not repeat or stack onto the older same-session ledger revision/compiler phases. Empty candidates are valid. A returned response and valid JSON establish delivery and syntax only, not the correctness of its revisions.

Second-stage callers may select `revisionMethod: "mechanism-candidate-v2"` or `"mechanism-candidate-v3"`. Both separate an observed problem from its proposed mechanism, artifact change and test. V3 additionally checks a proposed change's factual premise, distinguishes catalog IDs from embedded references, and avoids treating either contradictory output field as ground truth. These are experimental opt-ins, not validated defaults; omitting the option preserves the original method. `reviewEventIds` can scope a complete first response to a source-closed local event packet. Other first-response events remain out of scope.

An `expert_operation_skill` artifact may explicitly declare `proposedCreation.integration` and a proposal destination. That declaration does not create a file or install a consumer. Existing materialized Card and evaluation-Skill targets remain distinct. Development results must retain regressions and source-attribution mistakes alongside any reviewable candidate; a method's improved proposal format does not prove better judgment.


`runLocalAlignerCandidate` in `src/harness-local-candidate-evaluation.ts` optionally tests an exact Card increment through the existing `runEvidenceAlignmentMode` and single-role Profile. It verifies the original Card text, preserves the full pair and uses an appended overlay. `runLocalCandidateFeedback` then sends actual current/candidate behavior to the second Harness; its decision remains a fallible proposal. The caller owns fixed cases, budgets and checkpoints. Local trials may set `maxCorrections: 0`; normal Expert evaluation retains the default of three correction attempts. A successful local invocation is not a promotion or production application.

`registerExpertReplayTool` and `createExpertReplayStore` in `src/expert-replay-session.ts` expose a bounded single-sample replay tool. The caller supplies a frozen input/configuration binding and an executor using the real Expert role. New run IDs execute; repeated IDs return existing results, including failed or started records. Pi callers must select `tools: "replay"` to expose `expert_replay`; `tools: "trace"` exposes only `trace_read`. The caller owns session persistence, shared provider accounting and the fresh-run cap. Repeated outputs are evidence, not ground truth, and proposed revisions are not applied automatically.

## Replay evidence contract

`runExpertReplayInvestigation` is the reusable Pi entry for the current Replay audit. It loads `.pi/skills/expert-replay-audit/SKILL.md`, builds the actual system/prompt, and selects `tools: "replay"`. The caller supplies the existing replay extension, frozen executor, session and budget; no additional reviewer or model layer is created. `buildExpertReplayInvestigation` exposes the same input construction for offline verification.

`expertReplayInputFromArchive` maps the complete Description and explicit user task purpose into current criteria, preserves both Aspects/Evidence and all historical observations, and excludes historical `matchRationale` from the current pair. It deliberately does not promote archived `criteria.skill` into current instructions. That generated artifact stays in its original archive; its useful general audit distinctions are expressed by the current operating Skill, and task-specific authority remains in the unchanged Description/purpose. Historical Cards and outputs remain labeled evidence rather than current rules.

The Skill separates Matcher concept comparability from Aligner's mode-dependent judgment, and separates raw Evidence from fallible extracted descriptions, citations and rationales. A proposed replacement reason/judgment remains separate from original output and is not a gold label. Include the returned version/Skill/system/prompt binding in the caller's replay cache identity; old sessions and payloads are not rewritten or silently upgraded. This interface change has offline coverage only, not a new claim of model effectiveness.
